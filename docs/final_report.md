## Project Goal

The goal of this project was to build a working video dubbing pipeline. The pipeline takes a YouTube video, transcribes the English audio, translates it into Spanish, generates Spanish speech with TTS, and then stitches the dubbed audio back into the original video.

The final output is a Spanish dubbed version of the original clip with captions. I focused mostly on making the pipeline more realistic by adding diarization, speaker-aware voice assignment, duration-aware translation shortening, better alignment estimates, and final stitching.

The project was much harder to get running than I expected. A lot of the work was not just writing code, but figuring out how to get the models and services to run without crashing. Chatterbox TTS was especially difficult because it kept timing out or becoming unstable when trying to process the full 170 segment video in one go. Diarization also caused issues because the environment was sensitive to dependency versions, and I had to use an older version of torchaudio and keep processing limited to one worker to avoid failures.

## Architecture

The project is split into a frontend, a backend API, and model services.

The frontend is the browser app. It lets the user run the pipeline stages and view the final video.

The backend is a FastAPI service. It exposes endpoints for downloading, transcription, diarization, translation, TTS, and stitching. The backend is responsible for moving data between each stage and saving artifacts into `pipeline_data/api/`.

The model services are used for Whisper transcription and Chatterbox TTS. In the Docker setup these run as separate services. In my Colab setup, I had to run the API and Chatterbox service manually because I was not using a normal local GPU machine.

The basic flow is:

Download video  
Transcribe audio with Whisper  
Run diarization to assign speaker labels  
Translate English segments into Spanish  
Generate Spanish TTS audio  
Align the generated audio to the original timing  
Stitch the dubbed audio with the original video using ffmpeg  

The main output folders are:

`pipeline_data/api/videos/` for downloaded videos  
`pipeline_data/api/transcriptions/whisper/` for transcripts  
`pipeline_data/api/translations/argos/` for translations  
`pipeline_data/api/tts_audio/chatterbox/` for generated TTS audio  
`pipeline_data/api/dubbed_videos/` for final MP4 outputs  
`pipeline_data/api/dubbed_captions/` for WebVTT captions

This was difficult to get working. The diarization setup was sensitive to package versions, especially torch and torchaudio. I had to use an older torchaudio version and keep the processing conservative. In practice, using one worker was more stable than trying to parallelize everything.

I added logic to merge speaker labels back into the transcript segments. The transcription output had 170 segments, and after diarization each segment could be assigned a speaker label like `SPEAKER_00`, `SPEAKER_01`, or `SPEAKER_02`.

The important part was making sure that the speaker labels did not just exist in the diarization output, but were actually usable by later pipeline stages. I added speaker merging so that transcript segments included the speaker field. Later, I also copied those speaker labels into the translated non-overlap transcript because the translated JSON originally did not preserve the speaker labels.

## Translation Reranking and Shortening

A big issue in this project is that translated Spanish segments can be longer than the original English time window. If the Spanish text is too long, the TTS either runs over the original timing or needs to be stretched too aggressively. That makes the dubbed video feel out of sync.

To address this, I implemented a duration-aware reranking function in `foreign_whispers/reranking.py`. The function `get_shorter_translations` takes the source English text, the baseline Spanish translation, the target duration, and optional previous and next context. It returns shorter Spanish candidates.

My approach was mostly rule based. I did not want to depend on an external LLM API at runtime. I used a character budget based on the target duration, then tried deterministic shortening strategies.

The function does things like:

Remove adjacent repeated words  
Collapse repeated connector patterns  
Remove filler phrases  
Replace longer common phrases with shorter synonyms  
Use word-boundary truncation only as a fallback  

An example of a useful shortening is:

`cerrado durante semanas y semanas y semanas`  
becomes  
`cerrado durante semanas`

This keeps the meaning mostly intact but removes repeated words that make the TTS take longer.

One issue I found was that my connector shortening rule was too aggressive at first. For example, it changed:

`y empiezas a ver el mundo`  
into  
`a ver el mundo`

That was bad because it removed too much meaning. I patched the reranking function so connector shortening only collapses true repeated connector patterns, like `semanas y semanas y semanas`, instead of deleting normal words at the beginning of a sentence. I also removed `a ver` from the filler phrase list because it can be meaningful inside a phrase.

After the patch, the bad example stayed unchanged:

`y empiezas a ver el mundo`

but the repeated phrase still shortened correctly:

`cerrado durante semanas y semanas y semanas`  
to  
`cerrado durante semanas`

This was one of the more important parts of the project because it directly affected whether the generated Spanish speech could fit into the original timing.

## Duration Prediction

The original duration estimate was based on a simple syllable rate. I tested several predictors against actual Chatterbox TTS ground truth durations from the generated segments.

The baseline estimate had a mean absolute error around 1.66 seconds, which was too high. I compared character count, syllable count, and a simple regression model. The simple regression using characters and syllables performed better than the basic heuristic.

The final estimate used:

intercept = 1.5380  
chars coefficient = 0.0072  
syllables coefficient = 0.1071  

The function estimates duration as:

`1.5380 + 0.0072 * chars + 0.1071 * syllables`

This brought the mean absolute error down to about 0.47 seconds on the available ground truth. The 5-fold cross-validation result was also around 0.49 seconds, so the improvement seemed real and not just from overfitting one run.

This helped the alignment policy make better decisions about whether a segment should be accepted, stretched, shifted, or shortened.

## Alignment and Optimizer

I also added a dynamic programming style global alignment optimizer. The goal was to improve over the greedy alignment baseline by keeping multiple possible partial schedules and choosing the lowest penalty path.

In practice, for the sample video, the optimizer tied the greedy baseline because there were no gap shifts and no severe stretch cases after the improved duration predictor. So this was more of an infrastructure improvement than a major visible quality improvement for this specific video.

Still, I think it is useful because a different video with more timing conflicts could benefit from a global optimizer instead of making every decision locally.

I also added a dubbing scorecard in `foreign_whispers/evaluation.py`. It reports scores for timing accuracy, naturalness, intelligibility, semantic fidelity, and an overall score. These are proxy metrics, not perfect human evaluation metrics, but they helped compare versions of the pipeline.

## Chatterbox TTS Issues

Chatterbox was the hardest part of the project. The full sample video had 170 segments, and trying to generate the whole thing in one normal run often caused timeouts or failures. Sometimes the Chatterbox process would become unstable, and the API call would hang for a long time.

To work around this, I used a restart-safe generation script. It restarts the Chatterbox service every 10 segment requests. I also forced TTS generation to use one worker because multiple workers caused problems when restarting Chatterbox while other requests were still running.

This was slower, but it was much more reliable.

The final generation process printed segment by segment logs, restarted Chatterbox every 10 requests, and eventually generated the full 170 segment WAV successfully.

## Non-Overlap Timing Fix

One of the biggest practical issues was that the original translated JSON had overlapping segment timings. When I generated the aligned WAV using those timings, the final audio was about 803 seconds long, while the actual video was only about 411 seconds. That made the dubbed video unusable.

I found that a non-overlap version of the transcript produced a WAV around 405.8 seconds, which was much closer to the original video duration. This fixed the biggest alignment failure.

The final demo uses the aligned non-overlap output. This made the video much more continuous and watchable. It is still not perfect, but it is much better than the version created from overlapping timings.

## Speaker-Aware TTS

After diarization and speaker label merging worked, I added speaker-aware TTS. The API accepts a `speaker_wav` parameter, and if no single speaker WAV is forced, it can use a voice map that assigns each diarized speaker to a specific reference WAV.

The final run used:

`SPEAKER_00 -> es/SPEAKER_00.wav`  
`SPEAKER_01 -> es/SPEAKER_01.wav`  
`SPEAKER_02 -> es/SPEAKER_02.wav`  

This allowed the final output to use different reference voices for the woman speaker and the two male speakers. It was not perfect, but it sounded better than using one default voice for the whole video.

One thing I learned is that reference clips matter a lot. My first `SPEAKER_00` clip had a bit of male voice at the beginning, so I replaced it with a cleaner clip from later in the video. That improved the voice reference.


### Voice Assignment Strategy

For the voice assignment strategy, I used a filename based approach with a default fallback. Each diarized speaker label maps directly to a matching WAV file in `pipeline_data/speakers/es/`.

The final mapping was:

`SPEAKER_00 -> pipeline_data/speakers/es/SPEAKER_00.wav`  
`SPEAKER_01 -> pipeline_data/speakers/es/SPEAKER_01.wav`  
`SPEAKER_02 -> pipeline_data/speakers/es/SPEAKER_02.wav`

I chose this approach because it is simple and easy to verify. If the diarization output says a segment belongs to `SPEAKER_00`, then the TTS system looks for `SPEAKER_00.wav`. If that file exists, it uses it as the Chatterbox reference voice. If it does not exist, the system falls back to `es/default.wav`, and then to the global `default.wav`.

The edge cases I considered were missing speaker-specific files, missing speaker labels, and translated segments that did not preserve the diarization labels. To handle this, I added fallback behavior in the voice resolution function and copied speaker labels into the translated non-overlap transcript when needed. This way the TTS stage could still run even if not every speaker had a custom voice file.

## Stitching and Final Output

The stitch step uses ffmpeg to combine the original video track with the generated dubbed WAV. It does not re-encode the video, so the original video quality is preserved. It also creates rolling two-line WebVTT captions.

For the final demo, I copied the best generated non-overlap per-speaker WAV into the aligned TTS output path and then forced the stitch step to rebuild the aligned MP4. I had to delete the old cached MP4 first, because otherwise the API would return the old stitched video instead of rebuilding it.

The final output video is the best version I produced. It uses:

Aligned non-overlap timing  
Spanish reference voices  
Per-speaker voice mapping  
Freshly stitched MP4 output
